# #185 real reset button, #184 fieldset disabled while a popup is open (developer notes)

Branch `feat/185-form-reset` from origin/master (f36e6448), with `origin/review/185` merged
(architect's rules 5 and 7, the review `memo/reviewer/review-185.md`).

## #185

- Cause: a click on `<button type=reset>` dispatches `reset` from a task, so a microtask
  checkpoint runs after each listener, before later listeners and the reset algorithm. Anything
  queued as a microtask in a `reset` listener (and a sync React commit it causes) sees the
  user's values and a `defaultPrevented` that later listeners can still change.
- The suite `packages/ui/src/__tests__/form-reset-button.browser.test.tsx` clicks **outside
  act** (`leaveActEnvironment`), as in a page. Inside `act`, `button.click()`, `fireEvent`, jsdom:
  all take the script order and hide the bug.
- **What was affected (my first audit was wrong to say "only Combobox")**:
  - Combobox text: read `input.value` in the microtask. Fixed in b15cee2e (computed target).
  - Field.Root: its own reset microtask refreshed error / `aria-invalid` / custom validity from
    the pre-reset values (review finding 1). Every control in a Field.
  - Rule 7 for every `useFormReset` caller and Field: a `preventDefault()` from React's
    `onReset` or a `document` listener was missed; the library dispatched a reset the browser
    did not perform (9 dispatches in my probe form, Chromium and Firefox).
- **Fix (architect's mechanism)**: `internal/after-dispatch.ts` `afterDispatch(event, cb)`: a
  microtask; if `eventPhase === NONE` run there, else `setTimeout(cb, 0)`. `useFormReset` uses
  it, and Field now goes through `useFormReset`. Script order unchanged (same task).
- I had tried the same mechanism myself before the coordinator said to wait; it went green
  the same way.

## Found on the way (not #185): Chromium drops a keystroke in a Combobox inside a Field

- Chromium only (Firefox fine), no reset involved: `<form><Field.Root validate={(_, d) =>
  d.get("text") === "bad" ? "No bad." : null}><Combobox.Root allowCustomValue
  defaultInputValue="Jap"><Combobox.Input name="text" />…` then click, Ctrl+A, type `bad`:
  the input ends at `ba`. The keystroke that flips the Field's validity (valid -> invalid) is
  lost. With `Field.Root required`, clearing the text (which flips to valueMissing) was lost
  too. A validate that never flips (always an error, or never) keeps every keystroke. Not
  investigated further; reported to the coordinator. The #185 Combobox-in-Field row uses a
  cross-field validate (another input makes it invalid) to stay clear of it.

## #184

- Chromium, Firefox and WebKit (CI probe branch `probe/184-webkit`, deleted): setting
  `fieldset.disabled = true` blurs the focused Input / Trigger (activeElement BODY), and the
  focus-leaving close hides the listbox: `[false, "BODY", false, 0]` for Combobox single,
  `multiple` and MultiSelect. Does not reproduce; no `:disabled` bail added.
- The guard rows now assert that premise with `settle` (activeElement is body, listbox closed),
  so an engine change fails with a clear message, and then the bail is owed.
- Contrast with conventions 3.6 / docs/research/button.md 1.2 (WebKit keeps focus on a button
  disabled *directly*): through a fieldset, WebKit blurs.
