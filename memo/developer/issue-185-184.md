# #185 real reset button, #184 fieldset disabled while a popup is open (developer notes)

Branch `feat/185-form-reset` from origin/master (f36e6448).

## #185

- Cause confirmed: a click on `<button type=reset>` dispatches `reset` from a task, so a
  microtask checkpoint runs after each listener, before the reset algorithm. `useFormReset`'s
  microtask (and the sync React commit an urgent setState in it causes) runs while `.value` is
  still the typed text.
- Probe file `packages/ui/src/__tests__/form-reset-button.browser.test.tsx`: the click is made
  **outside act** (`leaveActEnvironment`), as in a page. Inside `act` React would hold the commit
  until the click is over.
- Affected: **Combobox only** (single and its text; it read `input.value` in the microtask). Before
  the fix Chromium and Firefox both left `xyz` (not `""` as the issue said: the probe here used
  `allowCustomValue`; without it the blur reverts first) and a pick stayed `France`.
- Not affected (rows pass before the fix): NumberField (readDefault returns the computed target,
  visible `defaultValue` mirrored in onResetEvent), Slider (computed target), Select and
  `<selectedcontent>`, Checkbox, Switch, CheckboxGroup + Parent (also when nothing changed),
  MultiSelect (computed target), Combobox `multiple` (text target "" and computed values),
  OTPField (fixed in #171), RadioGroup (row already existed).
- Shared part: only the `useFormReset` doc comment (the contract: never read a reset result from
  `.value` / `.checked` in `onReset`). No new helper: every other caller already computes or reads
  `defaultChecked` / `defaultValue`, which hold the target before and after the algorithm.
- Controlled Combobox whose parent refuses the reset: DOM keeps the parent's text after a real
  click too (row "a parent that keeps its text").

## #184

- Chromium and Firefox: setting `fieldset.disabled = true` blurs the focused Input / Trigger
  (activeElement becomes BODY), the focus-leaving close hides the listbox, nothing to click.
- WebKit (CI only; it cannot launch here): the same. A throwaway branch `probe/184-webkit`
  (deleted afterwards) asserted `[openBefore, activeElement, openAfter, calls]` and got
  `[false, "BODY", false, 0]` on all three engines, for Combobox single, `multiple` and
  MultiSelect. So #184 does not reproduce; no `:disabled` bail was added. The rows stay as
  guards (the click branch only runs on an engine that keeps focus on the disabled control).
- Note the contrast with conventions 3.6 / docs/research/button.md 1.2 (WebKit leaves focus on a
  button disabled *directly*): here the control is disabled through its fieldset, and WebKit
  blurs.
