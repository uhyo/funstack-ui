# Review: feat/145-superseded-report-error (b6df202, f910b04) — #145, #150

Verdict: **merge after fixes** (findings 1 and 2 are behavioural regressions introduced by the
#150 fold; 3 is a test gap). #145 itself (reportError routing) is correct.

Probes were run in a scratch worktree of the branch (jsdom); branch jsdom suite is green apart
from `directives.test.ts`, which needs `dist/` (not built in the worktree).

## 1. Medium-high: exclusive ToggleGroup / exclusive Accordion resurrect the old item

`internal/use-controllable-action.ts:607-609` puts every uncontrolled dispatch of a component
that has a `reducer` into the burst fold. That includes the exclusive modes, which are
single-valued: `toggle-group/toggle-group-root.tsx:300-305` (replace only when `added` is
non-empty, else `applyPatch`) and `accordion/accordion-root.tsx:272-275` (`reduce`, close =
delete one item).

Reproduced:
- ToggleGroup `exclusive deselectable defaultValue="left"`: press Center (action rejects), press
  Center again (deselect; action called with `null`, resolves). Result: **Left pressed**.
- Accordion `exclusive defaultValue="a"`: click b (open, rejects), click b (close; action called
  with `null`, resolves). Result: **a open**.

The fold is `{left} -> (skip) -> remove center = {left}`. The user's last intent and the value
the resolved action was told are both "nothing"; the UI re-opens an item the user moved away
from. Before the branch (and with #145 alone) latest-wins committed `null`.
Fix: for single-valued modes commit the latest resolved `next` (fold with `(_prev, next) => next`,
or keep the latest-dispatch guard when exclusive); the developer's exclusive "replace on press"
rule is half of that. Add rows for "rejected press, resolved release".

## 2. Medium: CheckboxGroup form reset mid-burst can leave a non-default value

The reset is dispatched as a diff against `base()` (= latest in-flight `next`), see
`checkbox-group/checkbox-group-root.tsx:345-353`. The fold re-applies that diff onto the committed
value, so a value that an earlier, later-rejected dispatch had removed from `base` is never in
the reset's `removed`.

Reproduced: `defaultValue={[]}`, check a (resolves; committed [a]); uncheck a (will reject);
check b (resolves); click the form's reset (action called with `[]`, reason "platform",
removed [b], resolves); then uncheck-a rejects (reported). Result: **a checked**, b unchecked:
the form was reset but the group is not at its default, and the app's last resolved action was
told `[]`. Before the branch latest-wins committed `[]`.
Fix: a reset is absolute; let the reducer adopt `next` for the reset dispatch (as the Accordion
mount reconciliation does), e.g. by marking it in details/internally, rather than a diff.

## 3. Low: "dispatch order" unit row does not pin ordering

`internal/use-controllable-action.test.tsx:312` ("applies the resolved changes in dispatch
order") passes on the old latest-dispatch code too (latest `next` is `{b}` either way). A
discriminating row: a on, a off, b on, c on; resolve 2 before 1, reject 3 (superseded), resolve
4. Fold in dispatch order = {c}; resolution order = {a,c}; old latest-wins = {b,c}.
The other new rows (value-action-suite "commits only the settled changes", toggle-group #150
row, rewritten "superseded rejection" rows) do fail on the old code.

## 4. Low / unreachable: Accordion mount reconciliation behind a rejected click

`accordion-root.tsx:361-363` runs `reconcileOnMount` only in the Root's mount layout effect,
which is the Root's first possible dispatch (children do not dispatch from layout effects, user
events cannot interleave a commit). It re-runs only on an `<Activity>` re-show; then a pending
click's item has DOM open == optimistic, and `next` equals `base = latestInFlight().next`, so it
returns without dispatching. Judged unreachable; a comment in the reducer saying so would help.

## 5. Low: controlled/uncontrolled switch mid-burst

Entries recorded while uncontrolled still fold into `internal` after a switch to controlled
(invisible while controlled; reappears on switching back). Unsupported and warned; acceptable.

## 6. Low: docs

- ActionPropsPage overlapping-actions paragraph and SKILL.md say the fold applies to "ToggleGroup
  and Accordion with several items open" / "multi-item Accordion"; in code it also applies to
  exclusive Accordion and exclusive ToggleGroup (see 1). Align after fixing 1 (say "multiple"
  ToggleGroup).
- The set-valued paragraph should say that the resolved action's `next` includes earlier,
  still-pending changes (B's action receives [A, B]; the group then commits [B]); an app that
  persists `next` wholesale ends out of step with the UI, so persist `added` / `removed`.
- The rest checks out: React's isomorphic `startTransition` does pass an async action's
  rejection to the global error reporter; RoadmapPage entries are accurate.

## Checked, no finding

- Slider / NumberField: each rejection is caught in exactly one hook (step channel in
  `useActionTrigger`, commit channel in `useControllableAction`); superseded commits skip the
  rollback (`seq` check) and are reported once; the latest still rethrows in its transition. No
  double or missing reports. Removing the shared capture removes the #105 ordering constraint.
- Fold timing: `settle` calls `startTransition` from the action continuation; the pending async
  action entangles it, so it commits with the optimistic revert (the "|b" intermediate assertion
  confirms nothing commits early). A dispatch after the burst settled but before the fold renders
  composes correctly through the functional updater.
- Latest rejection as the last to settle: earlier resolved changes fold, then the boundary takes
  over. Consistent with #150.
- reportError stubbing: setup `afterEach` unstubs globals; no browser test makes an older action
  reject, so browser mode is unaffected today.
