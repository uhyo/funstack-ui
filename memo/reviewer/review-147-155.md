## #147

### H1. The restore is a `setAttribute("style", …)`, which a strict CSP blocks — the cut stays on (Chromium) or every inline style is wiped (Firefox)

`packages/ui/src/internal/css-transition-cut.ts:42-46` (the "nothing else wrote" branch):
`element.setAttribute("style", attribute)`. Under a CSP whose `style-src` / `style-src-attr` lacks
`'unsafe-inline'` (common; React's `style` prop keeps working there because React writes through
CSSOM, which CSP does not block), the attribute re-parse is blocked. Probe (page with
`<meta http-equiv="Content-Security-Policy" content="style-src 'self'">`, `width` set via CSSOM,
then the cut's set + restore):

- Chromium: `cssText` after restore = `width: 10px; transition: none !important;` — the cut is
  **left on the popup permanently**. Failure: a Popover with `transition="pop"` and a CSS exit;
  after the first library open, every later dismissal (Escape, click outside) snaps with no fade,
  and a consumer's own `style={{ transition }}` is dead; a CSP violation report per show / hide.
- Firefox: `cssText` after restore = `""` — **every inline style is dropped**, including React's
  (`style` prop sizes, Menu's point placement written as inline style). Failure: a context menu
  opened at a point with `transition` jumps to the anchor / default position after the show.

Only the absent-attribute path (`removeAttribute`) is safe. Fix: restore through CSSOM in both
branches (`style.removeProperty("transition")` or `setProperty("transition", previous,
priority)`, then `removeAttribute("style")` if the attribute was absent and `style.length === 0`).
Byte-for-byte identity of the attribute is not needed: React diffs its own props, never reads the
attribute. `style.cssText = attribute` also passes CSP (probe: restored correctly in both
engines). Add a jsdom-or-browser row with a CSP meta (browser: a dynamically inserted CSP meta
applies in Chromium) and adjust the docs' "puts your inline style back exactly as it was"
(TransitionsPage, conventions 5.1, the component JSDoc wording is fine).

### M1. The `:active-view-transition` gate is unpinned in the browser suites

`css-transition-cut.ts:34` `|| !viewTransitionActive(element)`. Mutation: removing the gate (cut
whenever `transition` is set) leaves all 283 Chromium browser tests of menu / popover / dialog /
combobox green. The jsdom row (gate off) tests the helper with a mocked `matches`, not that a
library show / hide with `transition` but **no** running view transition keeps its CSS enter /
exit — the fallback conventions 5.1 records ("a library close React batched into a
non-transition commit keeps its CSS exit"). Failure the suite would not catch: a refactor that
gates on the prop alone kills the CSS exit wherever React does not start a document view
transition. Add one browser row: `transition` set, close the popup with `flushSync` / an urgent
controlled `open={false}` (no view transition) and assert exit animations exist (Chromium) and
the content hold follows them.

### L1. Foreign-write branch can overwrite a `transition` written during the call

`css-transition-cut.ts:47-51`. If something writes inline style inside `run()` (a native
`beforetoggle` / `focus` listener of the consumer; React cannot re-render there) and that write
includes `transition`, the restore puts back the old `previous`, clobbering the new value. Guard:
only restore when `style.getPropertyValue("transition") === "none"` with priority `important`
(the cut's own value is still there). Rare; low.

### L2. Docs wording

- `packages/docs/src/pages/TransitionsPage.tsx` (#css-exit): "puts your inline style back exactly
  as it was" — not so in the foreign-write branch, and not under CSP until H1 is fixed. "they
  never overlap": a dismissal during a running library view transition still fades in the live
  new image; say "the library's show / hide never runs a CSS transition" instead.
- The cut is CSS **transitions** only: an exit written as `@keyframes` `animation` on the closed
  state is not cut and still double-images in Chromium. One sentence in #css-exit.
- SKILL.md says "do not add an `html:active-view-transition` rule"; RoadmapPage says you may keep
  it (with the unrelated-VT cost). Harmonise ("not needed; remove it").

## #155

### M1. A `<dialog popover>` (Popover's default) re-opened after a refused click-outside steals focus back from what was clicked

`use-popover-popup.ts:186` excludes `DIALOG` (correct: the dialog focusing steps run on every
`showPopover()`, the platform-probe row shows it). Probe (Chromium + Firefox): controlled
`open` kept `true`, click an `<input>` outside → fact → re-show → `document.activeElement` is the
popover's inner input. So a pointer user can never move focus to an outside field by clicking
while a refusing parent keeps the Popover open (keys typed go into the popover). The keyboard claim
holds: a Popover does not close on Tab, Tab leaves it; Escape re-focuses inside but Tab still
leaves. Not a regression (unchanged by this branch), and the setup is a dev-warned
misconfiguration. Ask: one clause in overlay-open-change.md 2.4 / PopoverPage ("a click outside
lands focus back inside the popover"), and a repo issue for the option of returning focus to the
element focused before the re-show (a `.focus()` against design 6.1, so a design decision).

### L1. BrowserOwnedStatePage wording

`packages/docs/src/pages/BrowserOwnedStatePage.tsx:210-214`: "a Menu or a Combobox ... A Popover or
a Dialog, a `<dialog>`, still gets..." — a Popover rendered as `<div>` behaves like the Menu.
PopoverPage says it right; align this one ("a Menu, a Combobox or a `<div>` Popover").

### Info (verified)

- Clearing: set only for non-echo closes in `onToggle` (353-356); cleared by any apply-effect
  run with `committed === false` (266) and by the consuming show (187). Uncontrolled and adopting
  controlled facts commit `false` (the fact's epoch re-renders the Popup) so the flag never reaches
  a genuine open; unmount drops the ref; `reshow` cannot see a set flag (the popup is shown).
  Mutation: dropping line 266 fails "an adopted Escape, then a keyboard open" (non-vacuous).
- Menu trap gone (probe, Chromium + Firefox): after a refused Tab-out, further Tabs move on
  (`next`, `next2`, …); Escape from the Trigger keeps focus on the Trigger; ArrowDown then focuses
  the first item (a real request). Skipping `resolveInitialFocus` also skips Menu's
  `takeOpenCause()`, harmless: every real open overwrites `openCause` in `onDispatch`.
- The Combobox row is a pin (Combobox never focuses), not a check of the fix; labelled as such.

### #147

- **H1 fixed.** `css-transition-cut.ts` now restores through CSSOM only (`removeProperty` /
  `setProperty`). The attribute is removed only if it started absent and the style is now empty;
  `removeAttribute` parses nothing. I ran a throwaway probe in Chromium and Firefox under
  `style-src-attr 'none'`, with a Popover that has `transition="pop"`, through a library open and
  close. Three consumer `style` props: a `transition` shorthand, longhands only
  (`transitionProperty` + `transitionDuration`), and none. In every case `cssText` and the
  computed `transition-property` / `transition-duration` after the open and after the close match
  the values before. The library's own `position-area` / `position-try-fallbacks` and `width`
  survive. React re-rendering `style` afterwards (adding `transition: color 1s`, then dropping it)
  lands correctly: the computed value follows and nothing is left behind. The new
  `css-transition-cut.browser.test.tsx` checks that the CSP meta is enforced (outside WebKit), so
  the row is not vacuous where it matters.
- **M1 fixed.** The new Popover row "a library close with no view transition: the CSS exit runs"
  fails in Chromium with the gate removed (I re-ran it).
- **L1 fixed.** The restore runs only while the cut's own `none !important` is present, and a
  jsdom row covers a listener that writes `transition` during the call. Residual nit (no action):
  a listener writing only a `transition-*` longhand other than `transition-property` is still
  overwritten.
- **L2 fixed.** "Never overlap" is reworded, the `@keyframes` limit is documented (TransitionsPage,
  SKILL, conventions 5.1), and SKILL and RoadmapPage now agree ("not needed: remove it; keeping it
  is harmless").
- **No regressions.** Popover, Menu, Dialog, Combobox and internal browser suites: 588 passed /
  16 skipped (Chromium + Firefox). jsdom `css-transition-cut.test.ts`: 9/9. CI 45296181198 /
  45296739400 green on all three engines.

### #155

- The dialog-popover click-outside focus steal is documented in overlay-open-change.md 2.4 and
  PopoverPage, linking #156. BrowserOwnedStatePage now names the `<div>` Popover with Menu and
  Combobox, and the `<dialog>` case as Dialog or default Popover. Accurate.
