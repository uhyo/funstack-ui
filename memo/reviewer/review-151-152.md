## Findings

### M1 (Medium, docs): "hidden" is wider than `<Activity>`, and two library features hit it
`internal/report-dropped.ts:12-13, 25-28`, `design/conventions.md:581-582, 604-608`, Toast page,
Dialog / Popover / Menu `keepMounted` docs, `design/components/menu.md` walkthrough 4.
Layout cleanup also runs when a shown Suspense boundary re-suspends (probed). Reachable through
library-owned features, not only a consumer's `<Activity>`:
- `keepMounted` overlays render content in `<Activity mode="hidden">` (`internal/overlay-popup.tsx:36`).
  Scenario: a `Dialog.Close` / `Menu.CheckboxItem` action pending, user presses Escape, the
  action rejects: reported, and the boundary is not shown on reopen. menu.md walkthrough 4 even
  recommends `keepMounted` for checkable items without saying this.
- Toast's own Suspense guard wraps the Action: an urgent `toast.update` whose new content
  suspends hides the Action; an Undo rejecting then is reported, while ToastPage says a rejection
  "reaches the nearest Error Boundary above the Viewport".
The behaviour is consistent with the chosen rule; the docs should say "unmounted or hidden
(`<Activity>`, `keepMounted`, a Suspense boundary showing its fallback)" and conventions 2.4's
"mounted and visible" should name Suspense.

### Info: race between rethrow and unmount
A latest rejection that arrives while connected and is rethrown, with the owner unmounting in
the same commit before React re-renders it, is still dropped by React. Tiny window, not worth
handling; maybe one clause in 2.4.

## The judgement call (Activity hide = gone, report only)
Agree, with a caveat. No React API distinguishes hide from unmount at rejection time (both run
layout and passive cleanup), so the options are: (a) report only (branch), exactly once, never
the boundary; (b) report and throw, boundary on re-show (React's behaviour) plus a duplicate
report, and if the hidden tree is later unmounted the throw is simply lost; (c) throw only, lost
on unmount (the #152 bug). Only (a) and (b) satisfy "never swallows". (b) is closer to React, but
for the library's own `keepMounted` overlays it means an Error Boundary fallback appearing when
the user reopens a dialog, possibly long after and out of context, which is worse UX than a
prompt `reportError`. Exactly-once also keeps the test contract simple. Since the user said in
#143 to align with React where possible, record this as a deliberate deviation needing the
user's/PO's confirmation (resolved question 43 currently presents it as an implementation detail),
naming (b) as the alternative.
