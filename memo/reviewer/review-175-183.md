## Nits / observations

N1. Escape row (overlay-close-part-suite.tsx, "Escape while the close waits"): it does not
assert the part's state between the dismissal and the resolve. The part stays data-pending,
hidden in a keepMounted popup, until openChangeAction(false) settles. Harmless, but undocumented.
Either pin it or leave it.

N2. Menu.Item still requests the close in the continuation (after a microtask), so the
synchronous prefix of openChangeAction(false) runs outside the click dispatch for an item, while
the Close parts keep it inside. This is the architect's choice ("as built"). Worth a line in
menu.md if anyone relies on user activation there.

N3. No browser row is needed for the race. The logic depends only on `toggle` being a task that
reads `details.open`. collapsible.browser.test.tsx:76 already checks, in real engines, that the
toggle caused by the library's own re-close is not dispatched. An optional real-engine row for
"re-open while a close is pending" (two separate tasks) would be cheap.
